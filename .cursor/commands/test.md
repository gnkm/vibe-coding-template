# テスト

## 概要

プロトタイプの品質を担保するためのテストを作成・実行するコマンドです。**最小限のテストで最大限の安心** を得ることを目的とします。

## 前提条件

- 技術スタックが決まっていること（参照: `docs/tech_stack.md`）
- テスト対象の機能が実装済みであること

## テスト方針（プロトタイプ向け）

プロトタイプ段階では以下の優先度でテストを作成する：

| 優先度 | テスト種別 | 目的 | カバー範囲 |
|--------|-----------|------|-----------|
| 高 | スモークテスト | アプリが起動し基本動作することを確認 | 主要な画面遷移、コア機能 |
| 中 | ハッピーパステスト | 正常系が動作することを確認 | 主要なユースケース |
| 低 | エッジケーステスト | 異常系の挙動を確認 | バリデーション、エラー処理 |

**プロトタイプでは「高」「中」を優先し、「低」は必要に応じて追加する。**

## 手順

### Step 1: テスト対象の確認

以下を確認し、テストの対象を明確にする：

| 確認項目 | 内容 |
|---------|------|
| 対象機能 | 何をテストするか |
| テスト種別 | 単体 / 結合 / E2E のどれか |
| 期待動作 | 何をもって「正常」とするか |

### Step 2: テスト環境の確認

技術スタック（`docs/tech_stack.md`）に応じたテストツールを確認する：

| 言語/環境 | 単体テスト | E2E/結合テスト |
|----------|-----------|---------------|
| JavaScript/TypeScript | Jest, Vitest | Playwright, Cypress |
| Python | pytest, unittest | pytest, Robot Framework |
| Rust | cargo test | - |

**テストツールが未設定の場合は、セットアップから行う。**

### Step 3: テストの作成

以下の原則に従ってテストを作成する：

#### 3.1 命名規則

```
[対象]_[条件]_[期待結果]
```

例：
- `login_validCredentials_redirectsToDashboard`
- `submitButton_emptyForm_showsValidationError`

#### 3.2 テスト構造（Arrange-Act-Assert）

すべてのテストは AAA パターンで構造化する：

```
テスト "ログイン成功時、ダッシュボードにリダイレクトされる":
    # Arrange（準備）
    credentials = { email: "test@example.com", password: "password" }
    
    # Act（実行）
    result = login(credentials)
    
    # Assert（検証）
    assert result.redirect_to == "/dashboard"
```

| フェーズ | 目的 | 例 |
|---------|------|-----|
| Arrange | テストの前提条件を準備 | テストデータ作成、モック設定 |
| Act | テスト対象の処理を実行 | 関数呼び出し、API リクエスト |
| Assert | 結果が期待通りか検証 | 戻り値、状態、副作用の確認 |

#### 3.3 テストファイルの配置

| パターン | 説明 | 例 |
|---------|------|-----|
| コロケーション | 対象ファイルと同じ場所 | `user.py` → `user_test.py` |
| 集約 | `tests` フォルダに集約 | `tests/unit/`, `tests/e2e/` |

**プロジェクトや言語の規約に従う。未定義なら提案する。**

### Step 4: テストの実行

作成したテストを実行し、結果を確認する：

| 言語/ツール | 全テスト実行 | 特定ファイル/テスト |
|------------|-------------|-------------------|
| npm (Jest/Vitest) | `npm test` | `npm test -- ファイル名` |
| Python (pytest) | `pytest` | `pytest ファイル名` |
| Rust | `cargo test` | `cargo test テスト名` |

### Step 5: 結果の確認

テスト結果を確認し、以下を報告する：

- [ ] 全テストがパスしたか
- [ ] 失敗したテストがあれば原因を特定
- [ ] カバレッジ（確認する場合）

### Step 6: 失敗時の対応

テストが失敗した場合：

1. **テストが間違っている場合** → テストを修正
2. **実装が間違っている場合** → 実装を修正
3. **仕様が不明確な場合** → ユーザーに確認

## 実行モード

### テスト作成モード（デフォルト）

指定された機能のテストを作成する。

```
/test ユーザー登録機能のテストを作成してください
```

### テスト実行モード

既存のテストを実行する。

```
/test 実行
```

### スモークテストモード

アプリの基本動作を確認する最小限のテストを作成・実行する。

```
/test --smoke
```

## スモークテストのチェックリスト

プロトタイプの最低限の品質確認：

### フロントエンド

- [ ] アプリが起動する
- [ ] 主要な画面が表示される
- [ ] 主要なボタン/リンクが動作する
- [ ] フォーム送信が動作する

### バックエンド

- [ ] サーバーが起動する
- [ ] ヘルスチェックエンドポイントが応答する
- [ ] 主要なAPIが応答する
- [ ] データベース接続が成功する

### E2E

- [ ] 主要なユースケースが通る（最低1つ）

## テストの種類と観点

### 単体テスト（関数・メソッド）

| 観点 | テストすべきこと |
|------|-----------------|
| 正常系 | 有効な入力に対して期待する出力を返すか |
| 境界値 | 0、空、最大値など境界条件での動作 |
| 異常系 | 無効な入力に対して適切にエラー処理するか |

```
テスト "calculateTotal":
    テスト "商品の合計金額を計算する":
        items = [{ price: 100, quantity: 2 }, { price: 200, quantity: 1 }]
        assert calculateTotal(items) == 400
    
    テスト "空の配列の場合は0を返す":
        assert calculateTotal([]) == 0
```

### UIコンポーネントテスト

| 観点 | テストすべきこと |
|------|-----------------|
| レンダリング | コンポーネントが正しく表示されるか |
| インタラクション | クリック・入力などのイベントが正しく動作するか |
| 状態変化 | 状態に応じて表示が正しく変わるか |

### APIテスト

| 観点 | テストすべきこと |
|------|-----------------|
| ステータスコード | 正しい HTTP ステータスを返すか |
| レスポンス形式 | 期待する形式のデータを返すか |
| エラーハンドリング | 不正なリクエストに適切に応答するか |

```
テスト "GET /api/users":
    テスト "ユーザー一覧を返す":
        response = GET("/api/users")
        assert response.status == 200
        assert response.body is Array
```

## 注意事項

- **過度なテストを書かない**: プロトタイプでは「動くことの確認」が最優先
- **壊れやすいテストを避ける**: 実装詳細に依存しないテストを書く
- **テストの保守コストを意識**: 価値の低いテストは書かない
- **手動確認で十分な場合もある**: すべてを自動化する必要はない
- **テストが通っても安心しない**: テストは品質保証の一部に過ぎない
