# 実装計画作成

## 概要

プロトタイプの実装計画を作成するコマンドです。設計書を元に、具体的な実装タスクとその順序を定義します。**動くものを最短で作る** ことを最優先とします。

**本計画は生成AIが実装することを前提としています。** AIのコンテキスト喪失に備え、各タスクはGitHub Issueとして登録できる粒度・情報量で記述し、1セッションで完結できるサイズに分割します。

## 前提条件

- PRD があること（参照: `docs/prd.md`）
- 技術スタックが決まっていること（参照: `docs/tech_stack.md`）
- 設計書があること（参照: `docs/architecture.md`）
- テンプレート: [assets/plan-template.md](assets/plan-template.md)

## 手順

### Step 1: 入力情報の確認

以下のドキュメントを確認し、実装の全体像を把握する：

- **PRD**: 機能要件、受け入れ基準
- **技術スタック**: 採用技術、開発ツール
- **設計書**: コンポーネント構成、ディレクトリ構成

**不足があれば先に該当ドキュメントの作成を依頼する。**

### Step 2: 実装フェーズの分割

以下の3フェーズで計画を構成する：

| フェーズ | 目的 | ゴール |
|---------|------|-------|
| Phase 1: 環境構築 | 開発環境を整える | `npm run dev` 等で起動できる状態 |
| Phase 2: 最小動作版 | コア機能1つを動かす | E2Eで1つのユースケースが動く |
| Phase 3: 機能追加 | 残りの機能を実装 | PRDの機能要件を満たす |

**Phase 2 完了を最優先ゴールとする。**

### Step 3: タスクの洗い出し

各フェーズについて、具体的なタスクを洗い出す：

- **タスクは30分で完了できる粒度**（GitHub Issue 1件相当）に分割する
- 各タスクには **完了条件** を明記する
- 依存関係がある場合は順序を明示する

**この粒度とする理由:**

| 観点 | 説明 |
|------|------|
| セッション完結性 | AIの1セッションで完了できるサイズ |
| コンテキスト喪失対策 | 新しいセッションでもタスク情報を読めば即座に再開可能 |
| 責任範囲の明確化 | 小さいタスクほどAIへの指示が明確 |
| 失敗時の影響範囲 | 小さいタスクなら巻き戻しが容易 |

### Step 4: 実装順序の決定

以下の原則で実装順序を決める：

1. **垂直スライス優先**: レイヤーごとではなく、機能単位で縦に実装
2. **依存の少ないものから**: 外部依存・他タスク依存が少ないものを先に
3. **確認可能な状態を維持**: 各タスク完了時に動作確認できるようにする

### Step 5: 実装計画書の作成

テンプレートに沿って以下を記述する：

1. **実装方針**: 全体のアプローチと優先順位
2. **フェーズ別タスク一覧**: 具体的な作業内容と完了条件
3. **リスクと対策**: 詰まりそうなポイントと回避策

出力先: `docs/plan.md`

### Step 6: レビュー依頼

作成した計画をユーザーに提示し、以下を確認する：

- タスクの粒度と順序の妥当性
- 見落としている作業
- 優先度の調整が必要な箇所

## 出力形式

```markdown
# 実装計画: {プロジェクト名}

## 実装方針
...（テンプレートに従う）
```

## 注意事項

- **完璧より動くもの**: 最初から完璧を目指さず、まず動く状態を作る
- **Phase 2 を死守**: 最小動作版の完成を最優先とし、それ以降は調整可能
- **タスクは具体的に**: 「〇〇を実装する」ではなく「〇〇ファイルに△△関数を作成する」レベルで記述
- **確認ポイントを明記**: 各タスクで何をもって完了とするか明確にする
- **コンテキスト喪失に備える**: 各タスクには必要な情報をすべて記載し、新しいセッションでも作業開始できるようにする
- **詰まったら戻る**: 実装中に計画と乖離したら、計画を更新する
