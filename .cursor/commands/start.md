# 計画外機能の実装開始

## 概要

計画外の機能追加を行う際に使用するコマンドです。既存の要求仕様（PRD）や設計書に沿った実装を補助し、**既存資産との整合性を保ちながら機能を追加** することを目的とします。

## 前提条件

- PRD があること（参照: `docs/prd.md`）
- 技術スタックが決まっていること（参照: `docs/tech_stack.md`）
- 設計書があること（参照: `docs/architecture.md`）

**いずれかが不足している場合は、先に該当ドキュメントの作成を依頼する。**

## 手順

### Step 1: 要求の把握

ユーザーの要求を以下の観点で整理する：

| 観点 | 確認内容 |
|------|----------|
| 何を追加するか | 追加したい機能・変更内容 |
| なぜ必要か | 背景・目的・解決したい課題 |
| どこまで実装するか | スコープ・完了条件 |

### Step 2: 既存ドキュメントの確認

以下のドキュメントを確認し、既存資産との関連を把握する：

| ドキュメント | 確認内容 |
|------------|---------|
| `docs/prd.md` | 追加機能が既存の機能要件と矛盾しないか |
| `docs/tech_stack.md` | 採用技術で実現可能か、新しい依存が必要か |
| `docs/architecture.md` | 既存のコンポーネント構成・データモデルとの整合性 |

### Step 3: 整合性チェック

追加機能について以下を検証する：

#### 3.1 PRD との整合性

- [ ] 既存の機能要件と矛盾しないか
- [ ] 対象ユーザー・ユースケースは既存と整合するか
- [ ] 優先度を考慮したとき、今実装すべきか

#### 3.2 設計との整合性

- [ ] 既存のコンポーネント構成に適合するか
- [ ] 新しいコンポーネントの追加が必要か
- [ ] データモデルの変更が必要か
- [ ] 既存の API・インターフェースへの影響はあるか

#### 3.3 技術スタックとの整合性

- [ ] 採用技術で実現可能か
- [ ] 新しいライブラリ・依存の追加が必要か
- [ ] 既存の設計方針（命名規則、ディレクトリ構成等）に従えるか

**整合性に問題がある場合は、実装前にユーザーに確認する。**

### Step 4: 実装方針の決定

整合性チェックを踏まえ、以下を決定する：

1. **実装場所**: どのファイル・コンポーネントに追加するか
2. **影響範囲**: 既存コードへの変更が必要か
3. **実装手順**: どの順序で実装するか
4. **確認方法**: どうやって動作確認するか

実装方針をユーザーに提示し、問題がなければ実装に進む。

### Step 5: 実装の実行

実装方針に従って実装を行う。実行時は以下を守る：

1. **既存の規約に従う**: 命名規則、コーディングスタイル、ディレクトリ構成
2. **小さく進める**: 大きな変更は分割して、こまめに動作確認
3. **既存機能を壊さない**: リグレッションに注意

### Step 6: 動作確認

実装完了後、以下を確認する：

- [ ] 追加機能が期待通り動作するか
- [ ] 既存の機能が壊れていないか（リグレッション確認）
- [ ] エラーや警告が出ていないか

### Step 7: ドキュメントの更新（必要に応じて）

追加機能の規模や影響度に応じて、ドキュメントの更新を検討する：

| 更新対象 | 更新が必要なケース |
|----------|-------------------|
| `docs/prd.md` | 新しい機能要件として追記すべき場合 |
| `docs/architecture.md` | コンポーネント構成やデータモデルに変更があった場合 |
| `docs/plan.md` | 今後の計画に関連する場合（補足として追記） |

**小規模な変更の場合、ドキュメント更新は不要な場合もある。ユーザーに確認する。**

## 実行モード

### 対話モード（デフォルト）

Step 4 で実装方針を確認してから実装に進む。

```
/start ログイン機能にパスワードリセット機能を追加
```

### 即実装モード

整合性チェックと方針確認を最小限にして実装を開始する。明確で小規模な変更向け。

```
/start --quick ボタンの色を変更
```

## 注意事項

- **既存資産を尊重**: PRD や設計書に記載された方針に従う
- **矛盾があれば確認**: 既存の設計と矛盾する場合は、実装前にユーザーに確認する
- **スコープを限定**: 1回の実装で対応する範囲を明確にし、スコープクリープを防ぐ
- **リグレッションに注意**: 既存機能を壊さないことを最優先する
- **適切な粒度でコミット**: 論理的にまとまった単位でこまめにコミットする
- **ドキュメント更新の判断**: 変更規模に応じて、ドキュメント更新の要否を判断する
