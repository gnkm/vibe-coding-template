# 設計

## 概要

プロトタイプの技術設計をおこなうコマンドです。PRDと技術スタックを元に、実装可能な設計ドキュメントを作成します。

## 前提条件

- PRD があること（参照: `docs/prd.md`）
- 技術スタックが決まっていること（参照: `docs/tech_stack.md`）
- テンプレート: [assets/architecture-template.md](assets/architecture-template.md)

## 手順

### Step 1: 入力情報の確認

以下のドキュメントを確認し、設計の前提を把握する：

- **PRD**: 機能要件、非機能制約、受け入れ基準
- **技術スタック**: 採用技術、構成方針

**不足があれば先に PRD 作成・技術選定を依頼する。**

### Step 2: 設計方針の決定

以下の観点で設計の方針を決める：

| 観点 | 検討内容 |
|------|----------|
| シンプルさ | プロトタイプとして必要最小限の構成か |
| 責務の分離 | 各コンポーネントの役割は明確か |
| テスト容易性 | 単体テストしやすい構造か |
| 拡張性 | 将来の変更に対応しやすいか |

**プロトタイプでは「シンプルさ」を最優先する。**

### Step 3: 設計書の作成

テンプレートに沿って以下を記述する：

1. **システム概要**: 全体像を1-2文で説明
2. **アーキテクチャ図**: コンポーネント間の関係を図示
3. **コンポーネント設計**: 各モジュールの責務と依存関係
4. **データフロー**: 主要なユースケースのデータの流れ
5. **ディレクトリ構成**: ファイル・フォルダの配置
6. **データモデル**: エンティティと属性
7. **API設計**（該当する場合）: エンドポイント一覧

出力先: `docs/architecture.md`

### Step 4: レビュー依頼

作成した設計書をユーザーに提示し、以下を確認する：

- アーキテクチャの妥当性
- コンポーネント分割の粒度
- 見落としている要件や制約

## 出力形式

```markdown
# 設計書: {プロジェクト名}

## 1. システム概要
...（テンプレートに従う）
```

## 注意事項

- **過度な抽象化を避ける**: プロトタイプでは直接的な実装を優先
- **図は必須**: Mermaid 等でアーキテクチャ図・シーケンス図を含める
- **命名規則を統一**: ファイル名、変数名、API パスの規則を明記
- **判断の根拠を残す**: 「なぜこの設計にしたか」を簡潔に記述
- **未決定事項は明記**: 後で決める必要がある項目には `(TBD)` を付記
